# 分析：JSNC202611 —— 端侧智能体验证工程（技术内参配套）

> 来源：https://github.com/kolibreath/JSNC202611 （单次提交 991f016，克隆于 2026-10-22）
> 分析方式：通读全部代码与文档，并在本机实跑单测、dry-run 全链路、dry 评测与判分器验证。

---

## 一、项目定位

这不是一个产品代码库，而是一套**银行手机银行场景的端侧大模型（端侧智能体）可行性验证工程 + 技术内参写作材料**。核心命题：

> 验证"端侧小模型（Qwen3-1.7B / Qwen3-4B-Instruct-2507，MNN int4）+ 自建 Harness"能否在手机本地完成
> **脱敏 → 意图路由（30 类 + OOS 拒识）→ 离线 FAQ / mock 工具 / 转云** 的全链路，并测出其能力边界。

仓库由两部分组成：

| 部分 | 内容 |
|---|---|
| 7 篇中文文档（约 230KB） | 1 篇内参主方案（含"四问要点结论"）、1 篇实施计划 v2（主设计文档）、6 篇背景调研（模型性能 / 工具调用 / WASM / 业界与银行聚焦 / MiniCPM / 适老化） |
| `edge-harness-poc/`（约 2500 行） | 全部工程代码：注册表、Harness、测试集构建、评测闭环、判分器、性能探针、单测 |

## 二、架构设计（工程侧最核心的资产）

**"PC 驱动 + 设备推理"**：Harness 与评测跑在 PC（Python），模型前向跑在 Android 真机
（MNN 交叉编译的 `llm_demo` CLI，经 adb 驱动），**不开发 Android App**——用等价性论证
（设计文档 4.1）换取工程成本数量级的下降。

代码分三层，职责清晰：

- **L1 适配层**（`harness/adapter_mnn.py` / `adapter_openai.py`）：三种后端同形接口
  （prompt 进、文本 + 计时出）。dry 桩适配器让无设备开发成为可能；openai 兼容适配器
  让设备到位前可用本机 llama.cpp server 跑真模型验证全管线——这是很务实的降险设计。
- **L2 模板与工具**（`harness/prompts/*.j2` ×4、`tools_mock.py`）：4 个 prompt 模板 +
  6 个带 `[MOCK]` 水印的 mock 工具。
- **L3 编排层**（`harness/pipeline.py`，约 220 行）：脱敏 → 意图分类 → 路由状态机的完整实现。

**注册表是单一事实源**（`registry/intents.yaml` 30 类意图 = 15 FAQ + 6 工具 + 9 转云 + OOS；
`registry/tools.yaml` 6 个工具），同一份 YAML 同时驱动 prompt 渲染、测试集构造、路由执行，
改一处即全链路生效。这个设计显著降低了一致性维护成本。

## 三、亮点：安全与合规是"硬编码"而非"提示词约定"

这是全仓库最值得学习的部分——安全规则全部落在代码层，不依赖模型自觉：

1. **PII 优先脱敏**：脱敏失败的安全兜底是"不放行原文、直接转云"（合规优先于可用）；
2. **高风险动作注册表硬编码**：转账/理财等 `route=cloud` 的意图由注册表决定转云，
   模型意见仅供参考（pipeline 注释原文："★ 高风险动作：注册表硬编码转云，模型意见仅供参考"）；
3. **工具白名单 + 调用上限**：白名单来自 tools.yaml 而非模型输出；单请求最多 2 轮工具调用，
   防端侧死循环；
4. **重试上限**：JSON 解析失败最多重试 1 次，之后走确定性兜底（转云话术），
   并记录 `fallback_reason` 审计字段；
5. **mock 数据强制水印**：桩返回一律带 `[MOCK]` 前缀，"演示物料不得去除水印"。

配套的**测试集对抗设计**同样到位：mask 子集 800 条覆盖"干扰物不误脱敏"（订单号/金额应保留）、
"轻度脱敏"等模式；PII 均为脚本按校验位算法生成的虚构值（README 有声明）。

## 四、评测闭环：先定标准，再测

- 四子集：intent 910 / mask 800 / tool 30 / faq 91（共 1831 条，已生成入库）；
- 三后端：dry（管线验证）/ mnn（真机）/ openai（本机 llama.cpp 过渡）；
- 四判分器 + **预设阈值**：macro-F1 ≥ 0.90、最差类召回 ≥ 0.85、OOS 拒识率 ≥ 0.85——
  "先定标准再测"的方法论是对的，避免结论被数据反向塑造；
- 单条异常不中断整批（`run_eval.py` 的 try/except + `__error__` 记账）。

## 五、本机实跑验证结果（2026-10-22）

| 验证项 | 命令 | 结果 |
|---|---|---|
| 单元测试 | `pytest tests/ -q` | **20 passed**（注册表 lint / 模板 / 解析器对抗 / 状态机 6 分支） |
| dry 全链路 | `python -m harness.pipeline --dry-run --input "帮我查下余额"` | 正确走 脱敏→query_balance(0.92)→get_balance→[MOCK] 播报，trace 计时完整 |
| OOS 分支 | `--input "今天天气怎么样"` | 正确判 out_of_scope → cloud_fallback，`fallback_reason=oos_or_low_confidence` |
| 评测闭环 | `run_eval.py --backend dry --subset intent --limit 100` | 100 行 0 错误，落盘 raw.jsonl + run.json |
| 判分器 | `rule_judge.py --run <run_id>` | 正常产出 report.json/md（dry 后端 accuracy=0.15，**符合预期**：桩适配器按关键词路由，不代表模型能力，run.json 内已自带该免责声明） |

结论：README 声称的"代码全部完成、单测全绿、dry 全管线验证"**与实跑结果一致，无夸大**。

## 六、文档质量

调研与方案文档不是代码的附庸，而是先行输入：6 篇调研（2025–2026 模型性能、端侧 Function Calling
现状、WASM 路线、业界落地、MiniCPM 盘点、适老化案例）→ 实施计划 v2（目标阈值/模型矩阵/
测试集构建方法/等价性论证/周计划）→ 内参大纲。"四问要点结论"已汇总（2026-10-20），
写作里程碑明确。已知坑也如实记录（Qwen3 思考模式与 grammar 约束冲突 llama.cpp #20345、
MNN CLI 单轮退出需常驻改造、热节点路径因机型而异、8GB 中端机跑 4B-Q4 贴内存红线且
"OOM 本身是结论素材"）。

## 七、风险与待办（按优先级）

1. **【最高】仓库公开性与保密要求矛盾**：README 明确写"本仓库含行内技术研究文档与评测方案，
   **请保持仓库为 private**"，但该仓库当前**可被公开克隆**（本次分析即未经认证克隆成功）。
   若确为行内材料，应立即改为 private 并排查泄露面；若不涉密，应删除该声明避免误导。
2. **真机链路全部未验证（自认）**：W1 全部阻塞在"设备到位"；`MNNAdapter.generate` 目前是
   "每条一个进程"的临时实现，批量评测前必须完成 D4 常驻改造（设计文档给了 A/B/C 三方案），
   否则每条重载模型，性能数据不可用。`Timings` 的设备侧打点字段（t_device_start/end）
   尚未接线，TTFT 扣除 adb 开销的口径要等 D4 落地后才真实。
3. **"CI lint"名不副实**：intents.yaml 注释称编辑规则"CI lint 强制"，但仓库无 `.github/`
   等 CI 配置，实际只有 `tests/test_registry.py` 手工/手动触发。建议补一个 GitHub Actions
   或至少在 CONTRIBUTING 里说明。
4. **三项行内输入阻塞 W2**（README 自认）：30 类意图需按行内 App 功能树修订；15 张知识卡
   `[占位示例]` 数值需业务双审；测试集 LLM 增广需行内大模型 API。冻结 v1.0 前这些不过，
   测试集的业务代表性存疑。
5. **faq 判分暂为规则版**，LLM-as-judge 排在 W2；FAQ 子集仅 91 条，是四个子集中最小的，
   统计功效有限。
6. 工程 hygiene 良好：`.gitignore` 正确排除模型权重与评测产物（本次实跑产生的 reports
   不会污染仓库）；单次初始提交，尚未冻结版本，符合其所处阶段。

## 八、总体评价

**这是一份"研究工程化"的范本**：把可复现性（单一事实源注册表 + 生成式测试集 + 预设阈值）、
合规安全性（代码层硬编码兜底）、开发体验（dry/openai 双降险后端）三件事在约 2500 行内
平衡得很好，且文档先行的组织方式让接手者可以按 W1 任务板直接开工。主要短板全部集中在
"真机未接入"这一未完成状态上（自认且有序号化地管理着），以及上述保密性与 CI 两个
名实不符的小缺口。对做端侧智能体可行性验证的团队，其 registry + harness + eval 三件套
的结构可以直接借鉴。
